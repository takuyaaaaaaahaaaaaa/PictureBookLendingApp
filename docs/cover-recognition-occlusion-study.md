# 手で隠れる表紙の検索: 次の検証案

2026-10-08以降の調査・実装の履歴。表紙検索は製品アプリに統合した機能です。現在の仕様・データ保持方針は [表紙検索の設計](cover-recognition-design.md) を参照してください。以下の検討案や過去の閾値は履歴であり、現在の仕様を示すものではありません。独立実験は `Experiments/CoverRecognition` に分離しています。実物の定量精度と配布前の権利条件は引き続き未確認です。

## 実機で分かったこと

- 登録本「ねむりの森」の手動撮影では最高類似度 0.879–0.882。候補閾値を 0.90 から暫定 0.85 に下げると候補を表示できる。
- 未登録本で確認された値は約 0.6–0.7。「0.8」の測定は対象の本を特定できないので、正例・負例のどちらにも算入しない。
- ライブカメラは映像を取得したが、初回の実機検証では Vision が表紙の四隅を検出できず、自動検索が始まらなかった。手で縁を隠すとこの方式は特に不安定になる。
- 現行の画像切り抜きが正しい表紙を常に選んでいるか、目視と実本の比較で未検証。スコアの変動だけから正しい切り抜きとは言えない。

## 方式の比較

| 方式 | 手による遮蔽 | iPad 実装 | 判断 |
| --- | --- | --- | --- |
| 現行: Vision の四角形検出 → 台形補正 → FastViT 全体特徴量 | 四隅や辺を隠すと検索自体が止まる | 既に検証版に実装 | 主要経路には不向き。撮影補助として残す |
| 固定領域・複数サイズの切り出し → 現行 FastViT | 角に依存しないが、手や背景も特徴量に混ざる | 追加モデルなしで試せる | 短期の比較対象。未知本の誤候補を厳しく測る |
| 局所特徴点 + 対応点の幾何検証 | 隠れていない部分に十分な特徴点があれば照合可能 | XFeat の Core ML 化と照合器の実装・計測が必要 | 次の本命 PoC |

## 論文・実装

- [XFeat: Accelerated Features for Lightweight Image Matching (CVPR 2024)](https://arxiv.org/abs/2404.19174): 軽量な局所特徴点と 64 次元の記述子を抽出する。公式実装は [verlab/accelerated_features](https://github.com/verlab/accelerated_features) で、リポジトリのライセンスは Apache-2.0。公開評価は画像対応・位置推定であり、絵本や手による遮蔽での精度ではない。公式実装は PyTorch を使用し、Core ML 版は提供されていないため変換と動作検証が必要。
- [LightGlue: Local Feature Matching at Light Speed (ICCV 2023)](https://arxiv.org/abs/2306.13643): 画像間の局所特徴を照合する追加モデル。公式 [実装](https://github.com/cvg/LightGlue) のコードと LightGlue 重みは Apache-2.0。SuperPoint は別の制限的ライセンスなので、XFeat との組み合わせや単純な相互最近傍照合を優先して検討する。
- [Unifying Deep Local and Global Features for Image Search (ECCV 2020)](https://arxiv.org/abs/2001.05027): 全体特徴量で検索してから局所特徴で検証する設計の根拠。絵本表紙の性能を保証するものではない。

## 最小の次期 PoC

1. 四隅検出を検索開始の必須条件から外す。カメラ中央のガイド領域を複数サイズで試し、現行モデルの候補が連続するフレームで安定した場合だけ表示する。貸出は自動確定しない。
2. 別のローカル実験で XFeat の公開重み・ライセンス・入力と出力を確認し、Core ML に変換できるか検証する。未知の実装を実行したり PyTorch / coremltools などを導入したりする前に、必要なものを報告する。
3. 書籍 ID ごとに局所特徴点を端末内へ保存し、候補上位に限ってカメラ画像との対応点を探す。対応点数だけでなく幾何的な整合性で候補を確認する。表紙の一部が隠れても、見えている箇所が一致すれば検索できる構成。
4. 実物の登録本、似た絵柄、未登録本、手で 10/25/40% を隠した場合、向き・反射・距離の違いを同じ条件で測る。候補正解率、未知本の誤候補率、検索時間、発熱を分けて記録する。画像・特徴量・蔵書データは端末外へ送らない。

手で主要な絵柄や文字を大きく隠す場合、どの方式でも識別情報が不足する。候補を出せないときは手動検索へ案内する。

## 2026-10-09: 登録画像を先に確認する

- ユーザーの指摘により、自動検索の方式変更より登録側の前処理確認を優先。
- 検証版の「表紙」→「登録画像を確認」で、現在の元画像、四角形補正後、実際の入力バッファを画像化した256×256入力を並べる。入力は中央正方形の切り出しであり、縦長の表紙の上下が欠ける。
- 既存索引に入力画像はないため、表示は現在の画像からの再現。保存済み特徴量とのコサイン類似度も表示する。外部書影は公開URLから再取得するため登録時との画像同一性は保証しない。検査は登録・索引を書き換えない。
- 合成画像による診断では元画像側は保存値とほぼ一致したが、補正側の再計算一致度は0.99118257だった。再検出・補正を含む処理の差の原因は未特定で、実物の認識精度を表す測定ではない。最初の「補正側も0.999以上で再現する」という診断用期待は失敗したため、前提として採用しない。確認画面は実測値をそのまま表示する。
- 自動テストは元画像側の再計算一致、256×256入力生成、検査による索引不変、外部書影で補正経路を使わないことを検証する。表紙を正しく切り抜けたかは実物の画像で確認する。

## 2026-10-09: 手動範囲指定と連続自動照合の検証版

- 「登録画像を確認」→本→「範囲を修正」で四隅の丸またはスライダーから軸に沿った矩形を指定する。台形の手動補正は未対応。
- 元の蔵書画像は変更しない。検索用の元画像スナップショット、範囲、元画像の参照情報、指定IDを端末内の索引とは別の `CoverFeatures-v1.json.crops.json` に保存し、選択した本の特徴量を更新する。手動指定がある本は背景を含む元画像側の特徴量を照合に残さない。
- 指定IDで索引との整合を確認し、モデル変更で索引が破棄された場合も指定範囲から再構築する。画像差し替え・書籍削除時は古い指定を無効化する。この検証用の範囲指定は端末内のみで、当時は既存の蔵書バックアップへ未統合でした。現在は形式2に含めて復元します。
- ライブカメラは約1秒間隔で元画像を送る。照合処理は端末内で1件ずつ実行し、同じ先頭候補が2回連続したら候補選択画面へ進む。候補なしでもカメラを止めない。画面終了や手動撮影への切替後の古い照合結果は採用しない。
- 四隅検出は任意の補助になり、検索開始の条件から外した。0.85の暫定閾値は維持。未登録本の誤候補を防げる保証はなく、登録本・未登録本を実機で比較する必要がある。
- 確認テスト: 既存の索引/外部書影テスト2件に、手動範囲の保存・再読込・モデル版変更による再構築・画像差し替え・不正範囲拒否、および連続一致/不一致/候補なしによる判定リセットの2件を追加。

## 2026-10-09: 閾値0.70の試行

ユーザーから、手動切り抜き後は認識が正確になった印象、未登録本の平均類似度は約0.6との報告。明示依頼により候補閾値を0.85から0.70（以上）に変更する。自動検索の2回連続一致と候補選択は維持する。平均値だけでは未登録本の上限や誤候補率は分からないため、実機で登録本・未登録本を引き続き比較する。画像や索引の再登録は不要。

## 2026-10-09: 「図書を追加」の撮影後確認

- 登録撮影ではUIImagePickerの標準正方形編集を無効化。向きを正規化した撮影画像から表紙の四隅を推定し、「表紙の切り抜きを確認」へ進む。自動推定できないときは写真全体を表示して調整を案内する。
- 「範囲を調整」で四隅をドラッグ、または角を選んで左右・上下スライダーで修正する。交差・画像外・極小の指定を拒否し、台形補正後の画像を再確認できる。「この表紙を使う」を押すまでフォームの画像は変更しない。
- 撮り直し・キャンセルに対応。フォームをキャンセル/リセットした場合は、このフォームで作成した未保存の画像ファイルを削除する。
- 採用した画像を図書として保存したら、確認済み範囲全体を検索用に登録し、もう一度自動で内部の四角形を切り抜くことを防ぐ。楽天の自動入力で既存の撮影画像を失わないよう保持する。
- 単体・統合テスト: 画像方向、縦長の手動切り抜き（背景除去）、不正な四隅の拒否、既存の索引テストを合わせて7件成功。合成画像による機能テストであり実物の認識精度ではない。
- 指定されたローカルSecrets.xcconfigを用いた楽天APIのライブテスト2件成功。公開書籍「ぐりとぐら」の検索、書影のHTTP200応答と画像デコードを確認（大200×145、小64×46）。キーはリポジトリ・結果ログに出力せず、検証用ビルドへの設定反映も値を表示せず確認した。
- シミュレータには実カメラがないため、架空の写真を確認画面へ渡してUIを確認。カメラから確認画面への実際の遷移、手で持った表紙の自動切り抜き位置はiPadで確認する。
- シミュレータで「範囲を調整」→角のスライダー変更→「切り抜きを確認」→「この表紙を使う」とキャンセルを操作し、補正結果の変化・採用・未保存を確認。撮り直しの実カメラ遷移は未検証。通常の検証版を指定のiPadへインストールし、起動成功（既存TestFlight版とは別のBundle ID）。
- 追加・編集フォームに、ローカル撮影写真があるときだけ「写真を調整」を表示。現在保存されている写真から四隅編集へ直接進み、自動の再切り抜きはしない。採用まで画像参照は変更せず、新しい画像は図書保存までドラフトとして管理する。既に切り落とした画像外の範囲は復元しない。登録撮影の初期カメラはユーザー指定で外カメラに変更した。

## 2026-10-09: 自動入力と撮影写真の選択
